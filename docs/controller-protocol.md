# Controller protocol

Wii U Connect has two protocol layers:

1. **Phone ↔ PC** – JSON messages over a WebSocket (`/ws`), described below.
2. **PC ↔ Cemu** – the Cemuhook "DSU" UDP protocol, which Cemu already supports as a client. Wii U Connect
   runs the DSU *server*. See [DSU layer](#dsu-layer-pc--cemu).

Keeping these separate means the phone protocol can evolve (binary encoding, WebRTC data channels) without
touching emulator integration. It also means the emulator side can change (a Cemu patch, for example) without
touching the phones.

## Phone ↔ PC (protocol version 1)

Transport: WebSocket, text frames, one JSON object per frame. Endpoint: `ws(s)://<pc>:<port>/ws`.

Every message has a `type` field. The server **closes the connection** if it receives a frame that is binary,
over 4 KiB, not valid JSON, or of an unknown `type`, or if a field fails validation. Before closing, it sends
an `error` message where it can.

### Session flow

```
phone                                   server
  | --- hello(token, role, deviceId) ---> |   must be the first message, within 5 s
  | <-- welcome(slot, player) ----------- |   or error(...) + close
  | --- input(seq, buttons, ...) -------> |   on every change + at least every 100 ms
  | --- ping(id) -----------------------> |
  | <-- pong(id) ------------------------ |
```

### Client → server

#### `hello`

```json
{ "type": "hello", "protocol": 1, "token": "k3J9…", "role": "wiimote", "deviceId": "6f1c…", "name": "Pixel 8" }
```

| field      | type   | rules |
|------------|--------|-------|
| `protocol` | int    | must equal `1` |
| `token`    | string | the pairing token shown by the PC (QR code / URL `?token=`); compared in constant time |
| `role`     | string | `"wiimote"` or `"gamepad"` |
| `deviceId` | string | 8–64 chars `[A-Za-z0-9-]`, randomly generated by the phone and stored locally; used to give a phone back its previous slot when it reconnects |
| `name`     | string | optional, at most 40 chars; shown in the PC diagnostics UI only |

#### `input`

A **complete snapshot** of the controller state, not a delta. Snapshots are idempotent: if a message is lost,
the next one corrects the state, so a button can never stay stuck because one "release" event was dropped.

```json
{
  "type": "input",
  "seq": 1042,
  "buttons": ["A", "B"],
  "pointer": { "x": 0.512, "y": 0.430 },
  "stick": { "x": 0.0, "y": 0.0 },
  "motion": { "accel": [0.0, -1.0, 0.0], "gyro": [0.0, 0.0, 0.0], "ts": 1234567 }
}
```

| field      | type | rules |
|------------|------|-------|
| `seq`      | int  | 0 ≤ seq < 2^53, strictly increasing per connection. The server drops snapshots whose `seq` is not greater than the last one it applied. |
| `buttons`  | string[] | held buttons, at most 16 entries, no duplicates; names must be valid for the role (below) |
| `pointer`  | object or `null` | optional (missing = `null`; the phone app always sends it). Normalised screen position: `x`,`y` ∈ [0,1], with (0,0) at the top-left of the game image. `null` means the pointer is off-screen or tracking is lost. |
| `stick`    | object | optional. Nunchuk stick (Wii Remote) or left stick (GamePad), `x`,`y` ∈ [-1,1], +y = up |
| `rstick`   | object | optional, GamePad only. Right stick, same rules as `stick` |
| `motion`   | object or `null` | optional. `accel` in g, `gyro` in deg/s, both as `[x,y,z]` in the **DSU axis convention** (see below). `ts` is a monotonic timestamp in microseconds. |

Wii Remote buttons: `A B ONE TWO PLUS MINUS HOME UP DOWN LEFT RIGHT C Z` (`C`/`Z` are the Nunchuk).

GamePad buttons: `A B X Y L R ZL ZR PLUS MINUS HOME UP DOWN LEFT RIGHT L3 R3`. (Reserved: the GamePad role is
implemented in Milestone 5.)

All numbers must be finite. Values outside their range cause a validation error and are not clamped, because
out-of-range input signals a client bug.

#### `ping`

```json
{ "type": "ping", "id": 7 }
```

Used for latency measurement. The server replies with a `pong` that carries the same `id`.

### Server → client

```json
{ "type": "welcome", "protocol": 1, "role": "wiimote", "slot": 1, "player": 1 }
{ "type": "pong", "id": 7 }
{ "type": "error", "code": "bad_token", "message": "pairing token rejected" }
```

`slot` is the DSU slot (0–3) the phone is bound to. `player` is the human-facing number: the GamePad is always
player 0, and Wii Remotes are players 1–3.

Error codes: `bad_token`, `unsupported_protocol`, `invalid_message`, `role_unavailable` (all slots for that
role are taken), `timeout` (no `hello` within 5 s), `replaced` (the same `deviceId` connected again).

### Safety rules (server-enforced)

- **Disconnect releases everything.** When a socket closes, the slot's buttons are released, sticks are centred
  and the pointer is hidden immediately. The DSU slot itself stays "connected" with neutral input, so Cemu's
  bindings never break while the phone reconnects.
- **Staleness watchdog.** If no `input` arrives for 1000 ms, the server neutralises the slot, just as it does on
  disconnect. Phones send a snapshot at least every 100 ms, even when nothing changed.
- **Idle timeout.** A connection that sends nothing at all for 10 s is closed with `timeout`, so a phone that
  vanished without closing its socket (Wi-Fi drop, sleep) frees its slot.
- **Reconnect.** A phone that reconnects with the same `deviceId` gets its previous slot back if the slot is
  still free. If the old socket is still open, it is closed with `replaced`.
- **Isolation.** Each slot has its own state. A message on one socket can only change the slot that socket is
  bound to.

### Slot allocation

| DSU slot | Role    | Player |
|----------|---------|--------|
| 0        | gamepad | 0      |
| 1–3      | wiimote | 1–3    |

Cemu's DSU client supports up to 4 slots per server (`DSUControllerProvider::kMaxClients = 4`), which matches
the four phones exactly.

## Protocol version 2: camera tracking (Wii Remote role)

> Status: implemented on the server (`crates/wiiu-connect/src/tracking.rs`) and in the phone app
> (`apps/phone/src/tracking/`). Tested end to end with synthetic JPEG frames, and with Chromium's fake camera
> playing the `/tracking` border into the real server. **Not yet tested on real phones.** See ADR-0001.
>
> The phone always sends `"protocol": 2` and accepts a `welcome` with 1 or 2. On version 1 it hides camera
> pointing.

Version 2 is version 1 plus two messages, so a phone can let the PC compute its pointer from the camera. A phone
sends `"protocol": 2` in `hello`. The server accepts both 1 and 2 and replies with the version it accepted in
`welcome`. Binary frames are still rejected on version-1 connections.

### `camera_frame` (binary WebSocket frame, client → server)

Little-endian header followed by the image payload:

| offset | type | field | rules |
|--------|------|-------|-------|
| 0 | u8 | kind | `1` = camera frame |
| 1 | u8 | format | `1` = JPEG (baseline; colour or grayscale) |
| 2 | u16 | width | 160–1280, must match the decoded image |
| 4 | u16 | height | 120–960, must match the decoded image |
| 6 | u16 | reserved | `0` |
| 8 | u32 | seq | strictly increasing per connection |
| 12 | u64 | capture_us | phone monotonic clock, µs, when the frame was captured |
| 20 | … | payload | at most 65 536 bytes |

Rules: frames over 65 556 bytes in total are rejected (the connection closes). The server reads the JPEG header
on arrival, and a size that differs from the frame header closes the connection. The server processes at most one
frame per slot at a time and **drops** frames that arrive while one is in flight, so a slow PC never builds a
queue. At most 60 frames per second per slot are accepted; extra frames are dropped silently. Only the
`wiimote` role may send frames.

### `gyro` (text, client → server)

```json
{ "type": "gyro", "samples": [[1234567, 0.01, -0.20, 0.03], [1239567, 0.02, -0.18, 0.02]] }
```

Each sample is `[t_us, rate_x, rate_y, rate_z]`. `t_us` uses the same clock as `capture_us`. The rates are
angular velocity in **rad/s** in the W3C device frame (x right, y up toward the top of the phone, z out of the
screen), as `DeviceMotionEvent.rotationRate` reports in deg/s (beta = x, gamma = y, alpha = z), converted to
rad/s. 1–64 samples per message, at most 1000 samples per second. Timestamps strictly increase across
messages. Values must be finite and below 35 rad/s.

The server converts these rates to the rear-camera frame as `(x, −y, −z)` (portrait, unrotated image) and feeds
them to the pointer fusion (`wiiu_tracking::PointerFusion`).

### Pointer ownership

While a slot is receiving camera frames, the **server-computed pointer replaces** the `pointer` field of that
phone's `input` snapshots. Before the first tag fix, and while the phone points beside the screen, that pointer
is hidden. If no frame has arrived for 2 s, the phone's own `pointer` field applies again (for example, a
manual or touch fallback).

### `tracking` (text, server → client, about 10 Hz while frames arrive)

```json
{ "type": "tracking", "state": "tracking", "pointer": { "x": 0.41, "y": 0.62 }, "tags": 7, "fixes_per_s": 28.5 }
```

`state` is `tracking`, `gyro_only` or `lost`. Phones use it for on-screen feedback ("point at the TV").

## DSU layer (PC → Cemu)

Wii U Connect implements the Cemuhook protocol v1001 as a UDP server, on `127.0.0.1:26760` by default.
The packet layouts mirror Cemu's own client structs (`src/input/api/DSU/DSUMessages.h`, verified at Cemu
commit `aa20e2f`), and `crates/wiiu-dsu` tests them byte for byte.

### How Cemu consumes DSU data (verified in source)

- **Buttons:** Cemu maps the bits of `state1` and `state2` to `kButton0..15`, and the touchpad-click byte to
  `kButton16`. It ignores the `PS` (home) byte.
- **Pointer:** `DSUController::get_position()` returns touch point 1 (or 2) normalised by **1920 × 942**.
  `WPADController::WPADRead` turns that into the emulated Wii Remote's DPD/IR pointer (`pos = p * 2 - 1`,
  `dpd_valid_fg = 2`). An inactive touch point means "pointer not visible".
- **GamePad touch:** `VPADController` uses the same position for the GamePad touchscreen, which is the
  foundation for Milestone 5.
- **Motion:** Cemu reads the motion timestamp in µs, gyro in deg/s and accel in g, then calls
  `processMotionSample(gyro.xyz in rad/s, acc.x, -acc.y, -acc.z)`.
- **Subscriptions:** Cemu sends a data request after **every** packet it receives for a slot. The server pushes
  data to each subscriber until 5 s pass without a renewal.

### Button mapping (Wii Remote → DSU → Cemu profile)

| Wii Remote | DSU bit         | Cemu button id | Cemu Wiimote mapping id |
|------------|-----------------|----------------|-------------------------|
| A          | state2 Cross    | 14             | 1 |
| B          | state2 Circle   | 13             | 2 |
| 1          | state2 Square   | 15             | 3 |
| 2          | state2 Triangle | 12             | 4 |
| Nunchuk Z  | state2 L2       | 8              | 5 |
| Nunchuk C  | state2 L1       | 10             | 6 |
| +          | state1 Options  | 3              | 7 |
| −          | state1 Share    | 0              | 8 |
| D-pad ↑    | state1 Up       | 4              | 9 |
| D-pad ↓    | state1 Down     | 6              | 10 |
| D-pad ←    | state1 Left     | 7              | 11 |
| D-pad →    | state1 Right    | 5              | 12 |
| HOME       | state1 L3       | 1              | 17 |
| Nunchuk stick | left stick (lx/ly) | axis 38/39/44/45 | 13–16 |

Wii Remote HOME is carried on L3 because Cemu ignores the DSU `PS` byte. `wiiu-connect cemu-profile` writes a
Cemu controller profile with exactly these bindings, so you don't have to bind each button by hand in Cemu.
